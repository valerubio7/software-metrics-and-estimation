# Tareas: Registrar el esfuerzo realizado en una historia o tarea (US-15)

## Convención de commits

- Cada Unidad de Trabajo (UT) cierra con **un único commit** en la rama `feat/us-15-registrar-esfuerzo`, con Conventional Commits. Cada commit contiene pruebas, código y documentación de su unidad, compila y deja `go test ./...` en verde (las pruebas de integración se ejecutan con Docker disponible).
- **Regla de mensaje de commit (obligatoria para `sdd-apply`)**:
  - Asunto en Conventional Commits (los asuntos de cada UT están fijados abajo).
  - Cuerpo de **5 a 8 líneas como máximo**, con **una línea compacta** por cada fase: `RED: <1-2 nombres de prueba clave> falla/n (<motivo corto>)`, `GREEN: <1-2 nombres de prueba clave> pasa/n`, `REFACTOR: <cambio o "sin cambios de comportamiento"> (<resultado>)`. Se puede agregar una línea de `TRIANGULATE` y una de contexto.
  - **Sin salida pegada** de `go test`, sin logs ni trazas. La evidencia detallada (comandos, salidas, duración) vive en `openspec/changes/us-15-registrar-esfuerzo/apply-progress.md`.
  - Sin `Co-Authored-By` ni atribución de IA.
- **Evidencia de apply (obligatoria)**: al cerrar cada UT, `sdd-apply` DEBE crear o actualizar el archivo físico `openspec/changes/us-15-registrar-esfuerzo/apply-progress.md` (una sección por UT con RED/GREEN/TRIANGULATE/REFACTOR observados, comandos ejecutados y resultados, hash del commit) **además** de guardar el progreso en Engram (`sdd/us-15-registrar-esfuerzo/apply-progress`). El archivo se agrega al commit de la UT correspondiente.
- **Estrategia de entrega**: un solo PR (`delivery_strategy: single-pr`) con `size:exception` ya aceptado por el usuario. No se diseñan PRs encadenados.
- **TDD estricto**: cada ciclo es RED (prueba que falla y se observa fallar) → GREEN (código mínimo) → TRIANGULATE (casos adicionales que fuerzan generalizar o cubren bordes) → REFACTOR (sin cambiar comportamiento). Comando de referencia: `go test ./...`.
- Idioma: documentación y comentarios de prueba en español neutro; identificadores, rutas, SQL y códigos HTTP en inglés.

### Discrepancias entre spec y diseño (a resolver o confirmar)

La spec define el comportamiento y el diseño la estructura. Resueltas por el orquestador antes de esta fase:

- `created_at`: la tabla lo conserva y la entidad y la respuesta `201` NO lo exponen (D12/D13). La spec se alineó con esto; no se agrega `CreatedAt` a `EffortRecord`.

Discrepancias que permanecen (ninguna cambia el comportamiento de la spec; se listan para que no se resuelvan en silencio):

1. **Violación de FK de proyecto**: la spec (Requisito "Garantizar la integridad referencial", escenario "Una violación de clave foránea no produce `500`") menciona la traducción de FK de integrante, tarea, historia **y proyecto**. El diseño no define una FK directa a `projects` (la FK `effort_records_story_project_fkey` ya implica el proyecto) y `MapConstraintError` mapea solo tres restricciones. Tratamiento en estas tareas: `MapConstraintError` cubre las tres FKs reales; `ErrProjectNotFound` queda cubierto por la verificación transaccional (paso 1) y por una prueba del handler que verifica los cuatro sentinelas → `404` con su código (tarea 5.1). No se inventa una FK ni un mapeo de proyecto. Si se quisiera cumplir la spec de forma literal habría que ajustar la spec o el diseño: queda como observación para `sdd-verify`.
2. **Escenario "Un registro persiste solo si todo el alta se completa"** (`500 internal_error` y ningún registro tras un fallo del almacenamiento): la estrategia de pruebas del diseño no lo lista de forma explícita. Se agrega: caso `500` sin filtrar detalle en el handler (UT 5) y una prueba de integración HTTP con un `TRIGGER BEFORE INSERT` que lanza excepción, verificando `500` y cero filas (tarea 6.6).
3. **Escenario "Las horas acumuladas del día no se limitan"** y **descripción de 500 caracteres multibyte aceptada por la base**: el diseño no los enumera en la prueba de integración del repositorio; se agregan en la tarea 4.4 (TRIANGULATE) para cubrirlos contra PostgreSQL real.
4. **Escenario "Las rutas existentes no cambian"**: el diseño no define una prueba nueva. Se cubre con la suite existente de `tests/unit/cmd/api/` y `internal/api/` en verde más aserciones de `Tasks`/`SprintHistory` conservados en `effort_route_test.go` (tarea 6.1).
5. **README**: la propuesta pide una "fila nueva en la tabla de rutas", pero el README no tiene una tabla general de rutas de la API (solo la tabla de lecturas de la TUI, líneas ~80-83). Se confirma la interpretación del diseño: subsección breve nueva "API de esfuerzo" con una tabla de una fila, ubicada antes de `## Pruebas`. No se agrega el `POST` a la tabla de lecturas de la TUI.
6. **Ubicación de la prueba de readiness**: la propuesta menciona `tests/unit/api/`; el diseño la ubica en `tests/unit/cmd/api/effort_route_test.go`. Se sigue el diseño.
